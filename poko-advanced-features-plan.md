# Po-Ko Advanced Features Plan

## Top-Level Overview

This plan extends the Po-Ko Developer Framework with five interconnected feature areas:

1. **Daily Data Entry + Sick Day Logging** — a user-friendly daily log form so users can enter each day's wearable data to keep history current, plus a first-class "I'm sick today" button that labels those days for pattern analysis.
2. **Continuous Learning Engine with Dynamic Database** — migrates telemetry storage from a static JSON file to a lightweight embedded database (SQLite via `better-sqlite3`) that scales as history grows, then runs whole-history multi-metric pattern analysis using Bob as the AI reasoning layer. The engine does far more than threshold-tuning: it scans all biometric fields (HRV, Resting HR, Sleep Score, Stress, Body Battery, Respiration, Sleep Duration, etc.) over rolling windows to detect recurring multi-day signatures that precede sick days or high-fatigue episodes. When a pattern is confirmed across multiple historical instances, it is automatically registered as a new detection trigger in the scoring engine — with no manual configuration required.
3. **Contextual Health Advice Popups** — three fixed daily advice notifications (morning, midday, afternoon) generated by Bob from live metrics and external factors — specific, actionable, non-generic guidance tied to what the numbers actually say.
4. **UX Explainability Layer** — short in-UI descriptions, per-metric info buttons with tooltips, and a Po-Ko score breakdown panel so users can interpret everything without prior knowledge. *(Lower priority — implement only if Bob credits remain after Sub-Tasks 1–3 and 5.)*
5. **IBM Bob IDE Integration** — survey prompts, advice popups, and the Po-Ko score surfaced inside the IBM Bob IDE via the MCP server; the IDE is the primary interaction surface, the web dashboard remains a secondary full-view screen.

**Design Principle:** Simplicity first. Every UI element should be self-explanatory on first use. Complexity lives in the engine, not the interface.

**Answered design decisions:**
- Learning engine threshold adjustments → **auto-applied** after each analysis run (no user confirmation step needed).
- Learning engine scope → **whole-history, multi-metric pattern detection** — not just HRV thresholds; all biometric fields are analysed as a combined signature.
- Advice delivery timing → **fixed daily schedule** (morning ~8am, midday ~12:30pm, afternoon ~4pm) to build habit and support routines.
- Bob IDE integration → **IBM Bob IDE only** (MCP stdio transport); no VS Code extension scope for now.
- **Implementation priority:** Sub-Tasks 1 → 2 → 3 → 5 → 4 (Sub-Task 4 only if Bob credits remain).

**Scope boundary:** This plan does not modify the Po-Ko scoring algorithm's core weighting (40/30/20/10 split), add authentication, add multi-user support, or change existing API response contracts (only additive fields).

The daily log form must be simple enough to fill in under 2 minutes. ## Sub-Task 2 — Dynamic Database + Continuous Learning Engine

### Intent
Two related changes: (1) migrate telemetry (and survey + sick day) storage from flat JSON files to SQLite so the database can grow indefinitely and support efficient whole-history queries without loading everything into memory; (2) build a `server/learningEngine.js` that runs full multi-metric pattern analysis across the entire history, uses Bob as the AI reasoning layer, and **auto-applies** both refined thresholds and newly discovered detection triggers to the scoring engine.

**Why SQLite:** The current JSON-file approach reads the entire file into memory on every request. At 191 records this is fine, but at 500+ records with analysis queries it degrades. SQLite via `better-sqlite3` is synchronous, zero-config, single-file, and fits the local-first privacy model. No network database, no credentials.

**Migration strategy:** On first startup after the migration, the server reads the existing JSON files and seeds the SQLite database, then continues normally. JSON files are kept as backup but are no longer the live store.

**Learning engine scope — what it actually analyses:**

The engine goes well beyond HRV threshold tuning. It analyses every available biometric field — Overnight HRV, Resting HR, Sleep Score, Sleep Duration, Body Battery, Avg Stress, Respiration Rate, and external factors — as a combined multi-day signature. The goal is to find recurring patterns that, when they appear together across 2–4 consecutive days, reliably precede a sick day or a HIGH/CRITICAL Po-Ko score.

**Pattern detection process:**
1. For every sick day in the database, extract the biometric readings for D-3, D-2, D-1 (the three days before).
2. Compute the average profile of those pre-sick windows across all sick-day instances.
3. Look for combinations of fields that move together in the same direction on each occurrence (e.g., HRV drops + Resting HR rises + Sleep Score drops + Respiration rises across 3 consecutive days).
4. Count how many times this combination appeared and was followed by a sick day within 3–4 days.
5. If a pattern appears 3+ times with a sick-day outcome, it is considered a confirmed pattern.
6. Send the confirmed patterns to Bob with a prompt asking Bob to: (a) name each pattern, (b) describe what it means physiologically, (c) produce the detection logic as a structured rule (field + operator + threshold + window), and (d) suggest a plain-English user warning message.
7. The resulting rules are stored in `data/learning_insights.json` under a `detectedPatterns` array and are loaded by the scoring engine as additional triggers alongside the existing hardcoded ones.

**Threshold refinement (also included):**
In addition to new pattern detection, the engine also computes personalised threshold adjustments for the existing HRV drop bands and external factor correlations — same as previously planned.

**Example of a confirmed pattern output:**
```json
{
  "patternId": "pre-illness-triple-signal-01",
  "occurrences": 4,
  "description": "HRV below 7d baseline by >6%, Resting HR elevated by >4 bpm, Sleep Score below 70 — across 3 consecutive days",
  "sickDayFollowedWithin": "3 days in all 4 cases",
  "detectionRule": {
    "window": 3,
    "conditions": [
      { "field": "hrv_vs_baseline_pct", "operator": "<", "value": -0.06 },
      { "field": "Resting_HR_bpm_vs_baseline", "operator": ">", "value": 4 },
      { "field": "Sleep_Score", "operator": "<", "value": 70 }
    ],
    "allMustBeTrue": true
  },
  "warningMessage": "Your biometric pattern over the past 3 days closely matches 4 previous instances that were followed by illness within 3 days. Consider reducing workload and prioritising recovery today.",
  "autoApplied": true
}
```

### Expected Outcomes
- `better-sqlite3` installed on the server.
- `server/db.js` initialises `data/poko.db` with tables: `telemetry`, `external_factors`, `sick_days`, `daily_advice`. Exports typed query helpers.
- All existing API routes that read/write JSON files are updated to use SQLite. Existing JSON files are migrated on first start.
- `server/learningEngine.js` exists with `runAnalysis()` that:
  - Queries full telemetry + sick days + external factors from SQLite.
  - Runs the multi-day multi-metric pre-sick-day window analysis described above.
  - Also computes personalised HRV threshold adjustments and external factor correlations.
  - Serialises confirmed patterns + threshold adjustments into a structured summary.
  - Calls Bob MCP with the summary; Bob names patterns, writes detection rules, and produces warning messages.
  - Writes the full result to `data/learning_insights.json` with `lastRun` timestamp and `autoApplied: true`.
- `server/pokoScoring.js` loads `learning_insights.json` on each `calculatePoKoScore()` call:
  - Applies user-specific HRV thresholds from `insights.thresholds` if present.
  - Evaluates each detected pattern rule from `insights.detectedPatterns` against the last N days of telemetry. If a pattern matches, adds a warning to the score response identical in structure to the existing `poko_trend_details` object.
- `POST /api/learning/run` triggers analysis and returns the insights summary.
- `GET /api/learning/insights` returns the latest stored insights.
- A `LearningInsightsBadge` component on the dashboard shows last run date and the count of confirmed patterns found. Includes a "Run Analysis" button.

## Sub-Task 3 — Fixed-Schedule Contextual Health Advice Popups

### Intent
Three times a day — morning (~8am), midday (~12:30pm), afternoon (~4pm) — the system generates and delivers a contextual health advice message. The message is generated by Bob using that day's current metrics and active external factors, producing specific, actionable, non-generic guidance. Examples of the expected quality level:

- **Instead of:** "Make sure to eat something."
- **Good:** "Your body battery is at 34 and stress has been elevated since 10am — eating within the next 30 minutes prevents the glucose dip that compounds cognitive irritability and slows decision-making speed."

- **Instead of:** "Manage your cognitive load."
- **Good:** "Your HRV is 12% below your 7-day average and you have a deadline flagged today. Front-load your most complex work in the next 90 minutes before your HRV suppression typically deepens in the afternoon."

A static curated fallback bank handles offline/Bob-unavailable scenarios. Advice is stored once per day (refreshed each session) and delivered via web toasts on the web dashboard. The IBM Bob IDE delivery is handled in Sub-Task 5.

### Expected Outcomes
- `server/adviceEngine.js` with `generateAdvice(telemetryDay, externalFactors, sickDay, scheduleSlot)` — calls Bob with precise metric values and returns 1 specific advice string + the triggering metric(s). `scheduleSlot` is `'morning'`, `'midday'`, or `'afternoon'`.
- `server/data/advice_bank.json` — curated static fallback bank of ~15 non-generic entries, each with a `trigger` condition object and `text` string.
- `POST /api/advice/generate` endpoint — triggers advice generation for a given slot and stores result.
- `GET /api/advice/today` endpoint — returns today's three advice messages (any already generated for the current day).
- A server-side scheduler in `server/index.js` fires `generateAdvice()` at 8:00, 12:30, and 16:00 each day using `node-cron` (or a simple `setInterval`-based time check).
- `client/src/AdviceToast.jsx` — dismissable card component with: category badge (nutrition / sleep / stress / immune), the advice text, and a "Why this?" toggle that reveals the triggering metric. Styled consistent with existing dark theme.
- `App.jsx` fetches `GET /api/advice/today` on load and shows the most recent un-dismissed advice toast.

## Sub-Task 5 — IBM Bob IDE Integration (MCP Server)

### Intent
Make the IBM Bob IDE the primary interaction surface for Po-Ko. Three capabilities are exposed from inside Bob without opening a browser: (1) current Po-Ko score + risk level, (2) today's survey questions delivered as a Bob interaction, and (3) contextual health advice notifications appearing as IDE messages at the three scheduled times. The web dashboard remains a secondary full-view screen — no web functionality is removed.

A dedicated `server/mcp.js` file starts a standard MCP stdio server using the SDK already installed. It registers three tools. Shared business logic is extracted into utility functions so the Express routes and MCP tools share the same code without duplication.

- `server/mcp.js` registers three MCP tools: `get_poko_status`, `submit_survey`, `get_advice`.
